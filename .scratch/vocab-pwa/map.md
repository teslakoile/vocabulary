# Vocabulary practice PWA

Labels: `wayfinder:map`

## Destination

A working PWA, installed to your home screen, that you open daily to practice your 84-entry vocabulary list. Entries are CRUD-able in the app and synced to cloud storage, an LLM helps generate and refine their content, three card types drill each entry from recognition through to production, and a scheduled nudge brings you back each day.

## Notes

**Execution is in scope.** This map overrides wayfinder's plan-don't-do default. Tickets build things as well as decide them, and the map is finished when the app is in daily use, not when the spec is written.

**Domain**: personal vocabulary retention for professional register. The 84 entries are enterprise, consulting, and AI-industry vocabulary that Kyle collected because of their connotation, not their dictionary meaning. Content in this app must sound like Kyle's working world (enterprise AI, investment, platform engineering), never like a dictionary gloss. `gravitas` is not "seriousness"; `hyperscaler` is not "a large company".

**Single user.** Kyle is the only user. Do not build multi-user auth, sharing, or accounts beyond what sync strictly requires.

**Source list**: 84 entries, currently in Google Keep. 30 are multi-word phrases, 13 carry slash or "vs" forms, 1 is an explicit contrast ("community of practice vs center of excellence"). A verbatim copy is in `source-list.md` alongside this map.

**Skills every session should consult**: `/grill-me` and `/domain-modeling` for decision tickets, `/mattpocock-skills:prototype` for prototype tickets, `/mattpocock-skills:research` for research tickets. For any UI work, `/impeccable` and `/make-interfaces-feel-better`.

**Tracker**: local markdown. Tickets live in `.scratch/vocab-pwa/issues/`, numbered from `01`.

## Decisions so far

- [Practice model and scope](issues/01-practice-model-and-scope.md) — destination is a working daily-use PWA; three card types per entry (recognition, reverse recognition, cued production); one entry carries a `forms` array and an optional contrast flag; content is CRUD-able in-app with the LLM operating on live data; storage is cloud-synced; nudges are scheduled reminders.
- [CRUD scope inside the app](issues/04-crud-scope-inside-the-app.md) — the app owns everything and Keep is archived; content is LLM-generated at capture time, non-blocking and queued, with bare entries held out of review; correction is inline edit only; browse is a first-class screen; delete means archive with history retained.
- [iOS PWA capability constraints](issues/02-ios-pwa-capability-constraints.md) — home-screen install exempts the app from Safari's 7-day storage cap, so IndexedDB is a durable cache but never the system of record; a scheduled nudge requires a server job POSTing to APNs, so a backend is mandatory and a static host is ruled out; Background Sync is unimplemented and Periodic Background Sync is WONTFIX, forcing offline-first with flush on app open; Web Share Target is not implemented on any iOS version; installation cannot be prompted and `beforeinstallprompt` will never ship.
- [Spaced repetition algorithm landscape](issues/03-spaced-repetition-algorithm-landscape.md) — FSRS-6 via `ts-fsrs` 5.4.1 (MIT, 13.4 KB gzipped, no optimizer needed at this size); three card types under one schedule is ruled out because FSRS difficulty is a single scalar with no card-type feature, so split into 252 independent cards sharing one parameter set; load is exactly linear in card count, roughly 15-17 presses/day at 252 versus 3-7 at 84; the binding constraint is the intake ramp, so cap new cards at about 6/day.
- [Scheduling unit and algorithm](issues/05-scheduling-unit-and-algorithm.md) — all three card types kept as 252 independent FSRS cards sharing one parameter set, because making recognition multiple choice cut the load objection to about 2 minutes a day; FSRS-6 via `ts-fsrs` 5.4.1 on default parameters permanently; grades map from a binary right/wrong with no self-grading; intake caps at 6 new cards a day and everything starts from zero; **the app is an endless game, not a daily queue** — no session boundaries, no done state, answers persist as given, and when everything due is cleared it enters free play, which serves cards without updating any schedule.
- [Stack, hosting, and LLM key custody](issues/06-stack-hosting-and-llm-key-custody.md) — Cloudflare end to end: Pages for the PWA, Workers for the API and the cron-triggered nudge, D1 for the database, with Vite/React/TypeScript on the frontend; generation runs server-side so it makes progress while the app is closed; every key is a Worker secret; auth is a single shared secret with rate limits weighted to the generation endpoint; Kyle uses **both phone and laptop**, which makes sync conflicts real. Four free-tier facts must be verified before building, and Workers Cron on the free plan is the critical one.
- [Entry and review-state data model](issues/07-entry-and-review-state-data-model.md) — an entry holds **senses**, because `forms` was conflating inflections, synonyms, polar pairs, and contrast sets; cards hang off senses (~285 cards, ~2.2 min/day) so `trivial` and `nontrivial` are separate cards rather than a harsh grading rule; distractors are close, drawn from sibling senses first and a generated array second; `caution` (when *not* to use a word) is its own field; entry conflicts are whole-entry last-write-wins, review events are an append-only log deduplicated by client UUID and replayed in order, and free play is an event flag excluded from replay.
- [Review session UX](issues/08-review-session-ux.md) — **there are no modes**: one continuous queue serving due cards first (which count) then everything else (which does not), with the transition invisible and a quiet marker on counting cards, so free play is the default rather than something you opt into; the answer side shows everything after every card (word, definition, caution, example, and Kyle's own capture note); wrong cards requeue about 8-10 cards later within the current app-open; inline correction happens on the answer side without losing position; no streak, no daily count, no completion state.
- [Generation prompt](issues/12-generation-prompt.md) — **amended 2026-08-23: no model API at all.** The corpus is generated once in a Claude Code session and loaded in, which removes the Anthropic key, the generation Worker route, and per-entry cost, and reverses capture-time generation on ticket 04 (a captured word now sits bare until a session runs). The prompt, field shape, sense rules, 60/40 cue mix, and `prompt_version` all survive unchanged. Originally: Claude Opus 5 with tool-use-forced schema, generating 3-5 rotating cues per sense to blunt the memorisation risk; sense splitting approved as proposed (13 multi-form entries become 22 senses, ~93 senses and ~279 cards total); register recorded as enterprise AI and platform engineering in an investment context, talking to steering committees, sponsors, directors, MDs and boards, **inferred from one approved example rather than stated**; prompts are versioned with `prompt_version` per sense so a systematically bad output is fixed once and regenerated in bulk, which is what makes the no-review-gate decision survivable; `capture_note` stays as an optional never-blocking field.
- [Browse and search screen](issues/11-browse-and-search-screen.md) — a row is an entry (84, the number Kyle wrote down), not a sense; search reaches every text field including definitions and cautions, and **search is the real navigation** rather than the list; rows are a headword plus a one-line gloss; filters are All, Recent, Struggling, Pending, Archived plus tags; progress appears as a filter only and never as a per-row badge, so no dashboard reappears; tapping a row opens a read view using the same inline editing as a card's answer side, with no practise-on-demand.
- [Nudge mechanism and cadence](issues/09-nudge-mechanism-and-cadence.md) — the notification **is an actual card** from the rotation, tapping it opens that card, and since there is no daily queue there is never a zero-due day, so the iOS rule that every push must display something is satisfied by construction; 1pm every day including weekends, implemented as an hourly cron that fires when it is 1pm in Kyle's stored timezone so travel and DST do not break it; permission is requested at the first launch **in standalone mode**, because push on iOS is impossible before home-screen install; an ignored nudge does nothing, with no escalation or streak.
- [Browser-based LLM feasibility](issues/15-browser-based-llm-feasibility.md) — **no**, and tickets 06 and 12 are confirmed rather than amended. On iOS it misses by 4-5x: Safari tab memory is measured under 500 MB, so the largest model that fits is Qwen3-0.6B at q4 (0.40 GB) while Gemma 4 E2B's web build is 2.01 GB. Desktop Chrome is feasible (Prompt API enabled by default since Chrome 148) but irrelevant, because WebKit's position is formally `oppose` so no Safari path will ever exist, and capture happens on the phone. Both hybrids rejected: they produce two content qualities in one corpus with no review gate and break `prompt_version`. Economics settle it anyway, at about $4 for all 84 entries with Opus 5, under $2 via the Batch API.
- [Infrastructure and deploy](issues/13-infrastructure-and-deploy.md) — **live at the private `workers.dev` origin**. Workers Cron is confirmed free (5 per account), so the stack gate passed. D1 `vocabulary` created in APAC with all 6 tables applied; one Worker serves both the PWA and `/api/` via the assets binding, so no separate Pages project; hourly cron trigger armed; `AUTH_SECRET` and the VAPID keypair set as secrets. All six auth cases verified. Two limits found that were not on the list: 10 ms CPU per invocation on Free (which forced the incremental-application amendment on ticket 07) and 50 D1 queries per invocation.

- [Cold start and Keep retirement](issues/14-cold-start-and-keep-retirement.md) — **84 entries live in D1**: 95 senses, 285 cards, 48 days of intake at 6 a day, 403 cues at 61% work. Generated by four parallel sessions with no model API. One systematic flaw caught and fixed: definitions ran longer than every distractor, so the correct answer was the longest option **100%** of the time and recognition could be scored without knowing a word; all 475 distractors were regenerated at matched length and the rule is now enforced by the validator. Cards seed unstarted with an `intake_order`, so nothing is due until it is answered. Archiving the Keep note is Kyle's to do, and until he does, ticket 04's one-way migration has not happened.
- [Build the app](issues/16-build-the-app.md) — **the app is live and works**. The queue runs in the browser because offline-first demands it, with both sides sharing one FSRS module. `SENSE_GAP` had to be invented after watching it run: the three cards of a new word arrived back to back and the second and third were answered off the screen just read. Sync split into an ETagged corpus and a small state call, cutting a routine open from 80 KB to 3.7 KB. Two real bugs found by testing rather than reading: resent event batches were double-advancing the schedule, and the service worker cached `index.html` so no deploy would ever have reached the phone. Push is written but unverified: it needs a real device and a 1pm. **Amended:** installation was a hard gate and is now a dismissible hint, because the laptop is never standalone and D1 is the system of record anyway; desktop gained number-key answering; and push subscriptions became a per-device list, since the single column meant turning the nudge on in one place silently killed it in the other. **Amended again:** the shared key's floor dropped from 16 characters to 8, which required building the rate limiting ticket 06 asked for and this build never had. Two layers: the Workers binding is best-effort (40 concurrent wrong keys, 38 got through) and an exact D1 counter behind it. Effective ceiling is about 30 guesses a minute, or 7 million years for an eight-character key.

- [Build the app](issues/16-build-the-app.md) — **amended again 2026-08-23: plain definitions and a fourth card type.** Kyle read the cards in use and the definitions were systematically overwritten: 89 of 95 carried a second sentence explaining their own nuance and 41 opened with an aside, because ticket 12's "never a dictionary gloss" was executed as never stating the plain thing. Median definition length went from 183 characters to 76 and the connotation stayed in `caution`, which already carried it. `identify` joins the rotation as the mirror of recognition, definition as prompt and words as choices, second in intake order because choosing is easier than recalling: 380 cards, 2.9 minutes a day, 64 days of intake. The `cards` rebuild that allowed a fourth type deleted the 7-row review log through an `ON DELETE CASCADE` that D1 would not let a `PRAGMA` disable, which cost history but not schedule. Two more tells found by measuring: generation sessions converge on the same wrong words (one used `wordsmith` on 12 of 23 senses), and an alphabetical tie-break in the fix put the answer first or last on 89 of 95 cards.

## Not yet specified

- **Whether the `caution` fields read right to Kyle.** He has now read the definitions in use and they were wrong in a systematic way, which [Build the app](issues/16-build-the-app.md) records and `prompt_version` 3 fixed. `caution` has still never been read at scale, and it now carries the connotation work the definitions used to duplicate, so it matters more than it did.
- **Whether four definitions want splitting into senses.** `lean on`, `sponsorship`, `amenable`, and `broad` each bundle two or three meanings. The plain rewrite forced the question rather than answering it: `broad` now states only the coverage reading and `amenable` is the one definition carrying two facets in a single sentence, joined by "or". Kyle's call which meaning he actually wants.
- **Whether capture in the app is fast enough to beat Keep.** Carried from [Capture speed spike](issues/10-capture-speed-spike.md), still unmeasured. The clock starts at install.
- **What happens to a word captured in the app.** It sits `bare` and stays out of review until a generation session runs, and there is no trigger for that session. A pile of bare entries is the failure mode.

## Out of scope

- Multi-user accounts, sharing lists, or any social feature.
- Replacing Google Keep as a general-purpose note tool. Keep may stay as a capture inbox; this app owns the vocabulary list only.
- A native iOS or Android app. The destination is explicitly a PWA.
- Free-form production grading by LLM ("write a sentence, judge whether it reads naturally") as the primary practice mode. Considered during charting and set aside: LLM graders are agreeable and would tell you yes almost always, and per-rep latency and cost would work against a 3-minute daily habit. Revisit only if cued production proves to be memorization rather than learning.
